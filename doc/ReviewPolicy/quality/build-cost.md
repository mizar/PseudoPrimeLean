# ビルド費用

`BUILD-01`：局所ビルド、全体ビルド、変更時の波及範囲を区別する。実測時間、静的な依存分析、推定した再構築範囲、未実施の試験を混同しない。

静的なimport削減、増分ビルドの実測、クリーンビルドの実測は別々に報告する。依存数の削減を、測定していないビルド時間の短縮として扱わない。

`BUILD-02`：重い有限証明や数値認証を一律に拒否せず、更新頻度、import構造、並列性、必要な再検証と代替案を検討する。重大な性能悪化が具体的に確認された場合は修正を求める。性能への懸念だけで数学的な不正と同じ `block` を使わない。

ユーザーが波及試験の省略を指示した場合は実施せず、その範囲で確認できた証拠を報告する。

`BUILD-03`：検証と性能測定の目的を分ける。ユーザーが指定した検証は実施し、計画書に性能測定があるという理由だけで、成功した検証に加えて高コストの再構築を実行しない。まず既存のビルドログ、増分ビルド、成果物のサイズ、静的な依存分析など、追加費用の小さい情報で確認できる範囲を調べる。

`BUILD-04`：クリーンビルドなど、キャッシュを利用しない測定を行う前に、対象の直接・推移importと集約importを確認する。重い有限証明や数値認証が含まれる場合は、既存の実測記録、並列性、予想される時間とメモリ、代替手段を確認する。単一ファイルを指定しても依存先の再構築が必要になり、独立環境でも実行費用が小さいとは限らない。静的分析や過去の実測は見積もりとして扱い、今回の実測やビルド成功の証拠と区別する。

`BUILD-05`：追加の高コストな測定が必要と考えられ、ユーザーがその実行を指定していない場合は、目的、対象、見積もりの根拠、代替案と中止条件を示してから実施の要否を確認する。すでに実行が指示されている場合は、その指示と範囲に従う。波及試験の省略指示を、別の名称の測定で回避しない。

`BUILD-06`：実行中に想定を超える依存先の再構築や負荷が判明した場合は、必要性と中止条件を再評価し、必要なら処理を停止する。対象プロセスを確認して停止し、無関係な処理に影響させない。中断したビルドを成功と扱わず、時間、メモリと対象範囲の計測方法・限界を報告する。プロセスごとの作業セットを合計した値は、共有ページを重複計上するため、物理メモリの実使用量と区別する。
