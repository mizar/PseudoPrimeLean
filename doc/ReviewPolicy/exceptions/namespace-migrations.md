# 一般名前空間への所有者移設

`MIGRATION-01`：一般側から専用側への逆依存を避け、宣言の型、証明、利用側の依存を確認する。同じ名前空間のファイル分割と、所有者の変更は区別する。

作業用リポジトリの `20261031_refactor/migration_policy.py check` は一般側から専用側への直接・推移import、修飾付き参照を検査する。これは静的検査であり、宣言の数学的な所属や全体ビルドの確認を代替しない。

## 現行の作業手順

配置変更は、逆依存を生まない依存先から着手する。変更前に前提・主張・定義本体・証明の依存関係を確認し、移動先が必要とする共通の定義・一般補題を先に分離して検証する。移動先が適用側を参照せずに成立することを確認してから、依存する宣言と利用側を順に変更する。対象の依存経路に既存の逆依存がある場合も、先にその依存を解消する。後で修正することを前提に、一般側から適用側へのimportを残したり追加したりしない。

新規に逆依存を生む変更は禁止する。変更前後の直接・間接の依存経路を比較し、一般側から専用の適用側へ戻る新しい依存が生じていないことを確認する。importの経路だけでなく、宣言・定義本体・証明の参照も対象とする。変更後に新規の逆依存が判明した場合は、当該変更をロールバックする。ビルドの成功やimport件数の減少を理由に例外扱いしない。

必要な依存を外せず逆依存が残る場合は、宣言の配置を見直す。前提・主張に適用先固有の概念が必要なら適用側へ配置し、一般部分と適用部分が混在しているなら宣言を分割する。配置先を先に固定して逆依存を例外扱いしない。

移設前後の定理の型と利用側を確認し、関連モジュールと全体をビルドする。静的な依存範囲の変化と実測ビルド時間は区別して報告する。全体ビルドの時点は関連する移設・利用側の接続・対象検証をまとめたうえで、変更範囲と検証結果に応じて判断する。
